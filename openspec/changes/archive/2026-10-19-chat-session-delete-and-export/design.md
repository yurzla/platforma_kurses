## Context

См. `proposal.md`. Сейчас есть только чтение: `GET /chat/sessions`, `GET /chat/sessions/{id}/messages`,
`POST /chat/sessions`, `POST /chat/sessions/{id}/ask` + опрос `GET /jobs/{id}`. Доступ к чужой
сессии проверяет `ensure_session_access` (владелец или `admin`). В БД `chat_messages` удаляются
каскадом от сессии, а `jobs.session_id` объявлен **без** `ON DELETE CASCADE`, поэтому простое
удаление сессии упадёт на внешнем ключе. Панель ассистента (`web.js`) при статусе job'а `failed`
печатает `data.error` — техническое описание из worker'а.

## Goals / Non-Goals

**Goals:**
- Владелец (и админ) может безвозвратно удалить диалог; связанные сообщения и job'ы исчезают.
- Диалог скачивается одним файлом в Markdown и в PDF с кириллицей и без системных зависимостей.
- Пользователь больше не видит техническое описание сбоя; оператор видит его в админке и логах.

**Non-Goals:**
- Soft-delete, корзина и восстановление удалённых диалогов.
- Экспорт всех диалогов сразу, экспорт из списка истории (только открытый диалог).
- Изменение формата ответа модели, ретраев и статусов job'ов.
- Смена схемы БД и миграции.

## Decisions

- **Удаление — жёсткое, без миграции.** Порядок в одной транзакции: `DELETE FROM jobs WHERE
  session_id = ?`, затем `DELETE FROM chat_sessions WHERE id = ?`; сообщения уходят каскадом.
  Порт `ChatRepository.delete_session(session_id)` и `JobRepository.delete_by_session(session_id)`
  (второй нужен, чтобы не полагаться на поведение FK в разных развёртываниях).
- **Права — как у чтения.** `ensure_session_access` вызывается до удаления, поэтому `404`
  (нет сессии), `403` (чужая), `401` (аноним) совпадают с существующим контрактом истории.
  Идемпотентность не имитируем: повторное удаление даёт `404`, как и чтение удалённой сессии.
- **Экспорт — отдельный GET с query-параметром `format`.** `md` по умолчанию не делаем: явный
  `format` = явный ответ `400` при опечатке (`format=docx`), а не «неожиданный Markdown».
  Имя файла: `dialog-<session_id>-<YYYY-MM-DD>.<ext>`, заголовок
  `Content-Disposition: attachment; filename="..."`.
- **Markdown — чистый Python** в `application/chat_export.py`: заголовок (курс или «Все курсы»,
  дата начала, участник), затем для каждой пары сообщений блоки `### Вопрос` / `### Ответ` с
  временем; ответы ассистента переносятся как есть (Markdown сохраняется), источники — строкой
  `Источники: ...`, если `used_chunk_ids` не пуст. Формат детерминирован, покрывается unit-тестом.
- **PDF — `fpdf2` + встроенный `DejaVuSans.ttf`** (лицензия Bitstream Vera/DejaVu разрешает
  распространение). Шрифт кладём в пакет `adapters/export/fonts/`, читаем через
  `importlib.resources`, поэтому он попадает в wheel и в Docker-образ. Альтернативы отклонены:
  `reportlab` — тяжелее и всё равно требует TTF; `weasyprint` — системные библиотеки (cairo/pango)
  и раздувание образа; печать из браузера — не файл и зависит от браузера.
  PDF-рендер в адаптере `adapters/export/pdf.py`, чтобы `application`/`domain` не зависели от
  `fpdf2`.
- **Нейтральный текст ошибки — только в web.** `jobs.error` остаётся техническим (`Тип: сообщение`)
  и доступен в `/dashboard`, DLQ и логах. В `web.js` при `status=failed` и при сетевом сбое
  выводится «Произошла ошибка, попробуйте чуть позже.». Остальные тексты панели
  («Не удалось создать сессию.», «Ошибка постановки вопроса.», «Превышено время ожидания ответа.»)
  не меняются — единый текст для всех ситуаций не требуется.
- **Кнопки выгрузки — в панели, а не в истории.** Ссылки формируются из текущего `sessionId` и
  видны только в режиме диалога; скачивание идёт через web-прокси, который уже пропускает
  `content-disposition` (в списке вырезаемых заголовков его нет).

## Risks / Trade-offs

- [Удаление job'ов теряет историю запросов] → это осознанно: диалог удаляется целиком; агрегаты
  админки по остальным job'ам не затрагиваются.
- [fpdf2 + шрифт увеличивают пакет] → ~800 КБ; взамен детерминированный PDF без системных libs.
- [Длинные ответы в PDF] → перенос строк средствами fpdf2, разбиение на страницы автоматическое.
- [Экспорт ограничен последними сообщениями] → используем `get_history` с большим лимитом
  (10 000), чего достаточно для демо-объёма; при необходимости лимит вынесем в настройки.

## Migration Plan

Схема не меняется, миграции не нужны. Развёртывание: пересобрать образы backend и web
(`uv lock` обновляется из-за `fpdf2`), после чего дамп базы пересобрать не требуется — данные
не меняются до первого удаления/экспорта.

## Open Questions

Нет: объём выгрузки (текущий диалог), жёсткое удаление и набор прав (владелец + админ)
зафиксированы выше.
