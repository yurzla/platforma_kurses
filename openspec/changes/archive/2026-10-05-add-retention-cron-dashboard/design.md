## Context

См. `proposal.md` — Why. Текущее состояние: `MessageBroker.publish` пишет в Redis без лимита, `JobRepository` умеет только `get/add/mark_*`, в проекте нет ни авторизации, ни шаблонов, ни статики. Compose поднимает `api` и `worker`; периодических задач нет.

## Goals / Non-Goals

**Goals:**
- Ограничить рост Redis-стримов и таблицы `jobs` без внешнего cron-инструмента.
- Дать оператору единую read-only страницу и API по job/DLQ/стримам.
- Развязать maintenance-задачи с обработкой вопросов (отдельная очередь, отдельные сервисы).

**Non-Goals:**
- Ретенция пользовательской истории (`chat_messages`/`chat_sessions`) — не удаляется.
- Действия над DLQ из UI (requeue/discard) — только просмотр.
- Ролевая модель/SSO — только опциональный разделяемый токен.
- Строгая (не-approximate) обрезка стримов по времени.

## Decisions

**1. Ретенция Redis — approximate `MAXLEN` при публикации.**
Просто, не требует планировщика, ограничивает память. Альтернатива — периодический `XTRIM MINID` по времени: строже (не теряет свежие при всплеске), но сложнее и требует отдельного расписания. Выбрано `MAXLEN ~ N` с щедрыми лимитами (`redis_stream_maxlen`, отдельный `redis_stream_events_maxlen`).

**2. Purge job-ов через отдельную cron-очередь (`rag.cron`).**
Планировщик (`scheduler`) публикует задачу по таймеру; выделенный консьюмер (`cron`) выполняет её с XACK и DLQ. Альтернативы: фоновая задача внутри `worker` (смешивает maintenance с обработкой вопросов), внешний cron/systemd (менее наблюдаемо, вне compose). Отдельная очередь даёт наблюдаемость (метрики/DLQ в дашборде) и изоляцию.

**3. Извлечён общий consumer-loop (`application/consumer.py`).**
Логика `XREADGROUP` + reclaim + graceful stop переиспользуется `worker` и `cron`, чтобы не дублировать цикл. Обработка сообщения (ack/retry/DLQ) остаётся в каждом консьюмере.

**4. Cron-задачи без повторных попыток.**
Задача `purge_terminal_jobs` идемпотентна; при ошибке сообщение уходит в `rag.cron.dead`, а следующий тик планировщика повторит попытку. Это проще, чем attempts-логика воркера, и не создаёт «залипших» задач.

**5. Дашборд — серверный Jinja2 + небольшой vanilla-JS.**
Данные отдаёт read-only `/api/v1/admin/*`, страница рендерится Jinja2 и периодически подтягивает JSON. Альтернатива — SPA/JSON-only: лишний фронтенд-тулинг. Добавлена единственная зависимость `jinja2`.

**6. Авторизация — опциональный `ADMIN_TOKEN`.**
Пусто → доступ открыт (внутренний инструмент); задан → требуется токен через `Authorization`, cookie или `?token=`. Альтернативы: всегда включённая авторизация (лишнее трение для внутреннего инструмента), HTTP Basic (нужны учётки).

**7. Индекс `idx_jobs_updated_at`.** Ускоряет purge по `updated_at`; создаётся `CREATE INDEX IF NOT EXISTS` в миграции `0004`.

## Risks / Trade-offs

- Approximate `MAXLEN` может отбросить самые старые сообщения при бэклоге больше лимита → лимиты заданы с запасом; при необходимости — переход на `XTRIM MINID` по времени.
- После purge `GET /jobs/{id}` для очень старых job вернёт `404` → дефолт ретенции 7 дней, для polling некритично.
- Админка/DLQ раскрывают тексты вопросов и ошибок → при заданном `ADMIN_TOKEN` доступ закрыт; дефолт «открыто» — осознанный выбор для внутреннего инструмента.
- Удаление job-ов не каскадит на историю — история остаётся (by design).

## Migration Plan

1. `alembic upgrade head` добавляет `idx_jobs_updated_at` (IF NOT EXISTS) — безопасно на существующей БД.
2. Деплой: пересобрать образ, поднять новые сервисы `scheduler` и `cron`; существующие `api`/`worker` перезапускаются с тем же кодом.
3. Роллбэк: остановить `scheduler`/`cron`, вернуть прежний образ; индекс опционально удалить (`downgrade`). Обрезка стримов и удаление job-ов назад не восстанавливаются (ретенция необратима, что ожидаемо).
