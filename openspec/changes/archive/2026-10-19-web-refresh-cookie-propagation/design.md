## Context

`call_api` при 401 обновляет токен, сохраняет объединённый cookie в
`request.state.merged_cookie` и повторяет запрос. Но при следующем вызове `call_api` заголовки
снова собираются из `request.headers`, где лежит исходный (просроченный) access-токен.

Страница шага делает два вызова: `GET /steps/{id}` и `GET /courses/{id}`. Первый после refresh
успешен, второй снова получает 401; повторный refresh со старым refresh-токеном (он ротирован)
не проходит, и структура курса приходит пустой.

## Goals / Non-Goals

**Goals:**
- Все вызовы API в рамках одного запроса используют актуальный access-токен.
- Убрать зависимость числа вызовов от порядка refresh.

**Non-Goals:**
- Изменение API или формата токенов.
- Кэширование ответов или объединение вызовов в один.

## Decisions

- **Подставлять `request.state.merged_cookie` при сборке заголовков.** Если refresh уже произошёл,
  `call_api` заменяет заголовок `cookie` на объединённый (старые cookie + новые из `Set-Cookie`).
  Это использует уже существующий механизм и не меняет логику refresh.
- **Тест на странице шага.** Портим access-cookie после логина и проверяем, что страница шага
  содержит и прогресс, и ссылки на соседние шаги.

## Risks / Trade-offs

- [Cookie из `merged_cookie` может содержать устаревшие значения] → он собран из исходного
  заголовка с заменой имён, которые вернул refresh; refresh-токен тоже ротируется и попадает туда.
- [Параллельные запросы браузера] → состояние живёт в `request.state`, изоляция сохраняется.
