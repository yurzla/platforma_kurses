## Context

Существующий `embed_chunks` — ручной batch-скрипт. Веб-запрос не должен ожидать Ollama, а поток
вопросов не должен блокироваться задачами индексации.

## Decisions

### Отдельный stream и процесс

Добавляется `rag.index.requests`, отдельная consumer group и entrypoint indexer. API публикует
сообщение только после коммита курса или шага. Сообщения имеют `kind`: `course_description` либо
`step_upsert`. Indexer использует стандартный `consume_loop`, подтверждает
сообщение после успеха и переносит ошибочное сообщение в отдельный DLQ.

### Индексация только описания курса

Задача содержит `course_id`. Indexer читает текущие title/description из PostgreSQL, формирует
`"{title}. {description}"`, удаляет устаревшие description-чанки либо
создаёт или обновляет чанк с `source_type=course_description` и соответствующий embedding.
Поэтому несколько быстро следующих PATCH безопасны: обрабатывается актуальное состояние БД,
а не устаревший снимок из очереди.

### Индексация материалов шагов

Для `step_upsert` indexer читает актуальный текст шага и его курс из PostgreSQL. Текстовые и
видео-шаги сохраняются как чанки `theory`, остальные типы шагов — как `task`; текст режется по
тем же правилам 500 слов с overlap 50, что и batch-скрипт. Indexer обновляет изменённые чанки,
удаляет лишние и сохраняет embeddings только для нового текста. Удаление шага уже удаляет его
чанки и embeddings в транзакции CRUD, поэтому отдельного сообщения не требуется.

### Идемпотентность

Если текст чанка и embedding для активной модели уже совпадают, Ollama не вызывается. При
изменении текста обновляются и `content_chunks.chunk_text`, и строка `chunk_embeddings`.

## Risks

Индексация имеет eventual consistency: сразу после HTTP 201/200 курс может ещё не находиться
по семантическому поиску. Недоступность Redis после коммита означает, что задача не будет
поставлена; обработчик логирует ошибку и возвращает успешный CRUD-ответ, не отменяя сохранённый
курс.
