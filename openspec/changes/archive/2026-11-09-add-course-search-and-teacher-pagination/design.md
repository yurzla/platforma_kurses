# Design

## Context

См. `proposal.md`. Студенческий каталог уже использует серверную пагинацию и
конверт `{items,total,limit,offset}`. Список преподавателя возвращает плоский
массив и строится прямыми SQL-запросами в роутере.

## Goals / Non-Goals

**Goals:**

- Одинаковая семантика поиска на студенческих и преподавательских списках.
- Поиск до пагинации, чтобы `total` соответствовал числу совпадений.
- Тестируемость списка преподавателя без реальной БД.

**Non-Goals:**

- Не менять поиск в админ-панели и поиск job-ов.
- Не менять схему БД и миграции.
- Не добавлять полнотекстовый поиск — используется подстрочный `ILIKE`.

## Decisions

1. **Параметр `search` на обоих API.** Единое имя для каталога и курсов
   преподавателя. Пустое значение после `strip()` означает отсутствие фильтра.
2. **Поиск по `title` и `description`.** Наиболее ожидаемое поведение; для
   PostgreSQL используется `ILIKE` с экранированием `%`, `_` и `\`.
3. **Конверт для преподавательского списка.** `{items,total,limit,offset}`
   повторяет контракт каталога и даёт web-слою всё для пагинации.
   **BREAKING** для прямых клиентов эндпоинта; в проекте его использует только
   web-сервис.
4. **Новый метод `CatalogRepository` вместо прямого SQL в роутере.** Список
   курсов преподавателя переносится в `list_authored_courses` /
   `count_authored_courses`; так его покрывает `InMemoryCatalogRepository`.
5. **Web-слой сам считает страницы.** API отдаёт `total`, `limit`, `offset`;
   web формирует номер страницы, пагинацию и сохраняет `search` в ссылках.

## Risks / Trade-offs

- [Расхождение SQL и in-memory реализации поиска] → Обе реализации используют
  одинаковую семантику: case-insensitive подстрока по title/description.
- [Прямые клиенты `/api/v1/teacher/courses` сломаются] → В проекте клиент один
  (web-страница), он обновляется в этом же изменении; breaking отмечен в
  proposal.
- [Спецсимволы SQL LIKE] → Экранирование `%`, `_`, `\` и тесты на литералы.

## Migration Plan

Миграции БД не нужны. Откат — revert коммита.
